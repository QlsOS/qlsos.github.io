QlsOS architecture

This document is a general map of the system. For how exactly the split between common code and architecture code (the HAL) works, see docs/hal-design.md separately — here that question is only mentioned, not duplicated.

Boot (x86)

  1. The BIOS puts the first disk sector (boot/boot.asm, 512 bytes, signed with 0xAA55, with a disk signature and one active partition entry for BIOSes that want one) at 0x7C00 and hands control over in 16-bit real mode. Stage 1 saves the boot drive number, asks the BIOS whether it has the LBA extensions (else uses the geometry it reports) and reads stage 2 (sectors 1-2, loaded to 0x7E00). A read is trusted only after it was checked: a failed read resets the controller and retries with a smaller chunk, and stage 2 carries a magic dword at both ends so a missed or shifted sector is noticed.
  2. Stage 2, with no third-party libraries: collects the memory map via BIOS int 0x15/E820 (with fallbacks for BIOSes that have none: E801, 88h, int 0x12; this is the last moment when the BIOS is available at all), enables the A20 line (tested, not assumed: already on / fast gate / keyboard controller, each with a timeout), loads the kernel (from LBA 3, up to 512 KiB) into a TEMPORARY buffer at 0x10000 in chunks (real mode cannot address above ~1MB directly), checks its CRC-32 against the value the build put into the loader, builds a temporary GDT and switches to 32-bit protected mode (CR0.PE=1). A damaged kernel is never started: the loader prints BAD CRC (or DISK ERR / A20 ERR) on the screen and on the serial port and halts.
  3. Already in protected mode, BEFORE jumping into C code: it copies the kernel (rep movsd) from the temporary buffer 0x10000 to its real link address 0x100000 (1MB) — see below for why this is mandatory — and only then jumps to kernel/arch/x86/src/entry.asm (already at address 0x100000+).
  4. entry.asm sets the segment registers for the new GDT, zeroes .bss, sets up the stack, calls kernel_main() — from this moment we are in the common, arch-independent C code.

The details of the loader (why it was rewritten, what it checks, the image layout, usb.img) are in ARCHITECTURE.md, section "The bootloader on real hardware (goal 27)".

Why the kernel must live above 1MB (found in practice, not in theory)

The classic PC memory map reserves 0xA0000-0xBFFFF for VGA video memory (graphics modes) and 0xC0000-0xFFFFF for the BIOS/option ROMs — this is not ordinary RAM, but a real "hole" in the address space, which QEMU reproduces as well. Previously the kernel was linked at 0x10000, and over time its .bss (a 256KB kheap arena + everything else) grew so much that it ran exactly into this hole. Static variables that were unlucky enough to land in this range (kheap's free_list, the shell's cursor, etc.) physically did not store what was written to them — the write went "into video memory", and the read returned something other than what was written. The symptoms were all different and at first glance unrelated to each other: input in the shell "drifted" onto a random screen row, kmalloc crashed into a page fault at address 0xFFFFFFFF — and it was all the same cause. It was fixed by moving the kernel to 0x100000, the standard place for any real OS. The moral: if a static variable somewhere "loses" values for no visible reason — the first thing to do is check its real link address (nm), rather than immediately suspecting a race condition or the initialization order.

Boot (ARM)

ARM has no BIOS and no stage1 in the usual sense — QEMU (-M virt -kernel kernel-arm.elf) itself puts the ELF into memory (0x40010000, see kernel/arch/arm/link.ld) and hands control to the entry point in SVC mode. kernel/arch/arm/src/boot.S:

  1. Sets up separate stacks for the SVC and IRQ modes (a shared stack for both would be a bug: the interrupt handler would trample the stack of the interrupted task).
  2. Programs VBAR (the Vector Base Address Register) with the address of its own table of exception vectors (vectors.S) — without this the processor would look for the vectors at address 0x0, where we loaded nothing.
  3. Zeroes .bss manually (the ELF loader in QEMU does not guarantee that BSS is already zero in memory — on real hardware even less so).
  4. Calls kernel_main().

Memory map

x86: the kernel is linked with a base of 0x100000 (1MB — see the section "Boot (x86)" above for why exactly there, and not lower, and kernel/arch/x86/link.ld), the PMM manages the first 64MB of physical memory (a bitmap frame allocator on top of the E820 map; usable regions shrink inward to whole pages and reserved ranges always win), paging does an identity map of the first 256MB. Memory above that is not mapped, but the ACPI tables, which firmware puts at the top of RAM (~1GB on a 1GB machine, ~3.5GB on 4GB), are reached through paging_map_phys: a kernel-only window (directory entry 64, 0x10000000) onto physical memory. Ring-3 drivers get device memory and ports as handles (SYS_DEV_MAP, SYS_DEV_IO) in a user-area window at 0x70000000.

ARM: the kernel is linked at 0x40010000 (the QEMU virt machine keeps RAM at 0x40000000). Paging/MMU and the PMM are not ported to ARM at all yet (see docs/hal-design.md, the section "what is not ported") — kheap works as a static arena in .bss, with no tie to the physical memory map.

Directory structure

boot/boot.asm            — x86 bootloader (stage 1 + stage 2, real mode)
kernel/hal/hal.h          — the contract between the common code and the arch backends
kernel/include/           — arch-independent headers (task.h, handle.h, channel.h,
                             device.h, kheap.h, shell.h, vfs.h, ...)
kernel/src/               — arch-independent implementation (kernel.c, shell.c,
                             task.c, handle.c, channel.c, device.c, caps.c, kheap.c,
                             kprintf.c, vfs.c, qlsfs.c, ...)
kernel/arch/x86/          — include/ + src/ (asm and C) + link.ld — everything x86-specific
kernel/arch/arm/          — include/ + src/ (asm and C) + link.ld — everything ARM-specific
user/                     — ring-3 programs (ELF): dispatcher, services, drivers, shell, tests + crt0/linker script
tests/                    — host-side tests and the QEMU harness (`make test`, `make test-*`)
tools/                    — crc32 (image check), usb-write.sh
docs/                     — this documentation (the contract is in ARCHITECTURE.md)
Makefile                  — targets: `make`/`make run` (x86), `make arm`/`make run-arm` (ARM)

Extension points

If you need to add a new architecture (RISC-V and others are planned after v1.0.0, see ARCHITECTURE.md, "Platforms after v1.0.0"): create kernel/arch/<name>/, implement the whole set of functions from kernel/hal/hal.h (hal_console_*, hal_input_*, hal_timer_*, hal_irq_*, hal_cpu_*, hal_reboot/hal_poweroff, hal_context_switch, hal_new_task_stack, arch_platform_init, arch_extra_demo, hal_arch_name) — and all of kernel/src/ will work without a single edit. That is the whole point of the split described in hal-design.md.
